# C++ 应用层编码规则精简版

本文档提炼应用层、业务层、工具程序、服务程序和桌面后端逻辑的关键规则。
目标是用够用的 C++17 写出稳定、易维护、易测试的代码，而不是堆砌语言技巧。

## 1. 总体原则

1. 规则、设计约束和协作说明统一使用中文。
2. 新增代码默认遵循 C++17。
3. 修改遵循最小改动原则，不做无关重构。
4. 应用层优先级依次为：正确性、可维护性、可测试性、可观测性、清晰边界、性能、抽象复用。
5. 代码应优先清晰、稳定、可替换，避免炫技式实现。
6. 任何模块都应能说明：负责什么、不负责什么、输入、输出、失败表达、日志位置、测试方式、替换边界。
7. 企业级应用代码必须优先形成稳定边界：跨模块接口、错误模型、测试入口、运行状态都必须先于局部实现技巧确定。


## 2. 推荐语言子集

1. 优先使用：类与对象、RAII、`std::string`、`std::vector`、`std::array`、`std::map`、`std::unordered_map`、`std::optional`、`std::variant`、`std::unique_ptr`、`enum class`、`constexpr`、标准算法、短小 lambda。
2. `std::shared_ptr` 只在真实共享所有权存在时使用。
3. 可以使用简单模板，但不要把应用层写成模板库。
4. 谨慎使用：异常、运行时多态、复杂继承、宏、全局单例、多线程共享状态。
5. 默认不使用：复杂模板元编程、SFINAE 技巧、运算符 DSL、隐式全局状态、裸 `new/delete`、手动资源释放、巨型类。

## 3. 命名规范

1. 统一使用驼峰命名。
2. 类型名使用 `UpperCamelCase`。
3. 函数名、变量名、命名空间、文件名使用 `lowerCamelCase`。
4. 成员变量使用 `lowerCamelCase_`。
5. 常量使用 `kUpperCamelCase`。
6. 枚举类型使用 `UpperCamelCase`，枚举值使用 `lowerCamelCase`。
7. 测试文件命名为“被测文件名 + Test”。
8. 名称必须表达业务含义，禁止 `Manager`、`Helper`、`Util`、`Common` 这类空泛命名。

## 4. 文件与目录规范

1. 保持头文件和实现文件分离。
2. 类定义放在头文件中，实现放在源文件中。
3. 推荐按职责组织目录：`app`、`domain`、`service`、`infrastructure`、`ui`、`tests`。
4. 业务对象放在 `domain`，用例编排放在 `service`。
5. 数据库、文件、串口、网络等外部依赖放在 `infrastructure`。
6. UI 仅负责交互与展示，不承载业务规则。
7. include 顺序为：当前模块头文件、标准库、第三方库、项目公共头文件、当前模块私有头文件。
8. 新模块必须明确归属到上述分层之一，禁止“先放一起以后再拆”。
9. `service` 不得直接拥有串口、数据库、HTTP 客户端等具体基础设施类型，必须依赖抽象接口。
10. `tests` 目录中的测试代码必须按被测层级组织，不得把协议、服务、基础设施测试混在一个文件里。
11. 目录名称和文件名称只能用小写字母、数字和下划线，禁止使用大写字母和连字符。

## 5. 类设计规范

1. 一个类只做一类事，职责必须单一。
2. 禁止把解析、存储、通信、UI、配置加载混在同一个类里。
3. 构造函数只建立依赖关系，不做网络连接、线程启动、数据库迁移等重型动作。
4. 业务服务依赖抽象接口，不直接依赖具体串口、数据库、HTTP 客户端实现。
5. 优先组合而不是复杂继承。
6. 类的公开接口要直接表达业务意图。

## 6. 资源管理规范

1. 所有资源统一使用 RAII 管理。
2. 资源包括文件句柄、socket、数据库连接、线程、锁、事务、临时目录等。
3. 禁止裸 `new/delete`。
4. 智能指针优先级：直接成员对象、引用、`std::unique_ptr`、`std::shared_ptr`。
5. 能用栈对象就不要堆分配。
6. 析构函数必须正确处理线程、锁、句柄等生命周期收尾。

## 7. 错误处理规范

1. 一个模块内只能有一种主错误风格。
2. 可选错误风格包括：状态码、`std::optional`、`Result<T, Error>`、异常。
3. 业务层优先使用明确的返回结果类型；简单“可能不存在”场景可以用 `std::optional`。
4. `std::optional` 只表达“可能没有”，不表达失败原因。
5. 不要用异常表示普通业务分支。
6. 如果项目允许异常，只在应用边界统一捕获并记录日志。
7. 后台线程必须捕获异常，禁止异常逃逸导致线程静默崩溃。
8. 跨模块公共接口默认使用 `Result<T, Error>` 风格对象或等价设计，错误码必须可枚举、可断言、可记录。
9. `bool` 返回仅允许用于不会丢失业务上下文的纯判断接口，禁止用于 I/O、解析、启动、发送、重试等失败原因重要的操作。
10. 解析类接口必须区分“数据不存在”“格式非法”“校验失败”“依赖异常”等不同失败原因。

## 8. 函数规范

1. 单个函数只做一层抽象，只完成一件事。
2. 函数建议控制在 50 行以内，过长时拆分业务步骤。
3. 参数建议不超过 4 个，过多时使用请求结构体。
4. 输入和输出要分离，避免一个参数同时承担输入和输出语义。
5. 函数命名要直接表达业务动作和结果。
6. 公共接口要稳定、易测、易替换。

## 9. const 与参数规范

1. 能加 `const` 就加 `const`。
2. 不修改对象状态的成员函数必须声明为 `const`。
3. 大对象优先用 `const&` 传递。
4. 小型标量优先按值传递。
5. 只有经过评审确认有收益时，才为了性能引入可变引用输出。

## 10. 容器与数据处理规范

1. 顺序数据默认使用 `std::vector`。
2. 固定大小数据使用 `std::array`。
3. 文本使用 `std::string`。
4. 需要排序的键值数据使用 `std::map`。
5. 追求查找性能时使用 `std::unordered_map`。
6. 非拥有的连续视图使用 `std::span`。
7. 遍历默认使用范围 `for`。
8. 大量插入前应考虑 `reserve`。
9. 优先做批量操作，减少无意义的逐条调用。

## 11. 字符串与编码规范

1. 禁止使用 C 风格字符串拼接处理业务文本。
2. 优先使用类型安全的字符串拼接方式。
3. 涉及文件、网络、UI 的文本必须明确编码，默认使用 UTF-8。
4. 文本处理逻辑要避免缓冲区越界和截断风险。

## 12. 日志规范

1. 日志必须有统一级别：`trace`、`debug`、`info`、`warning`、`error`、`critical`。
2. 日志必须带足够上下文，至少包括关键对象、操作、错误原因。
3. 日志不能只写“失败了”，必须可用于定位问题。
4. 禁止记录密码、token、私钥、身份证号、银行卡号等敏感信息。
5. 必须对敏感字段做脱敏处理。
6. 后台线程、轮询服务、重试任务必须暴露可查询运行状态，不能只依赖日志判断是否健康。
7. 线程入口如果吞掉异常，必须同步更新错误状态，并保证调用方可观测。

## 13. 配置规范

1. 配置必须定义默认值。
2. 配置必须在加载后统一校验。
3. 配置错误要明确返回原因。
4. 禁止在业务代码中散落 magic number。
5. 公共阈值、超时、重试次数等常量必须集中定义。
6. 配置加载模块只负责解析与校验，不得顺带启动资源、打开连接或执行业务逻辑。

## 14. 多线程规范

1. 优先消息传递，尽量少共享状态。
2. 锁必须通过 RAII 管理，禁止手动 `lock/unlock` 成对散落。
3. 后台线程必须可停止、可回收、可观测。
4. 共享状态的所有权、锁粒度和生命周期必须清晰。
5. 线程退出路径必须可测试，不能依赖进程强杀收尾。

## 15. 分层规范

1. 推荐依赖方向：`ui -> service -> domain`，`infrastructure -> domain`，`app` 负责组装。
2. `domain` 不依赖 UI、数据库、网络库和具体基础设施。
3. `service` 负责用例编排，不承载底层通信细节。
4. `ui` 不写业务规则，不直接访问串口、数据库或协议细节。
5. 业务规则应落在 `domain` 或 `service`，而不是按钮点击回调里。
6. `app` 只做装配、启动和进程级生命周期管理，不放业务解析与协议细节。
7. `infrastructure` 可以依赖 `domain` 或 `service` 暴露的抽象，但 `service` 不得反向依赖具体基础设施实现。

## 16. 接口与数据对象规范

1. 接口名要表达业务语义，避免 `send(int, string)` 这类模糊设计。
2. 返回值不能同时承担多个含义。
3. “找不到”和“执行失败”必须能区分表达。
4. 纯数据对象使用 `struct`。
5. 有不变量、封装行为和状态约束的对象使用 `class`。
6. 数据结构默认提供明确的初始值。

## 17. 注释规范

1. 注释解释设计意图、业务原因、边界条件和约束。
2. 禁止重复代码表面含义。
3. 复杂规则、历史兼容逻辑和特殊时序要求必须写注释。
4. 无意义注释、过时注释和调试残留必须删除。

## 18. 测试规范

1. 每个业务模块都应有对应单元测试。
2. 至少覆盖：正常输入、非法输入、边界输入、依赖失败、超时、重试、状态迁移、并发相关逻辑。
3. 测试名称应表达场景和期望。
4. 测试代码命名和结构要求与正式代码一致。
5. 使用 fake 或 mock 隔离外部依赖，避免单元测试直接连真实串口、数据库、网络。
6. 测试文件存在并不等于测试生效；所有测试目标必须接入 CMake，并注册到 `ctest`。
7. 服务层测试必须优先使用 fake / stub 基础设施，不得默认依赖真实串口或真实设备。
8. 解析模块必须覆盖成功路径、错误路径和边界输入，不能只测 happy path。

## 19. 代码格式规范

1. 使用 4 个空格缩进，不使用 Tab。
2. 每行建议不超过 100 个字符。
3. 同一文件内风格必须一致。
4. 条件表达式过长时应拆成具名布尔变量。
5. 代码块层级过深时必须拆函数或提前返回。

## 20. 安全规范

1. 所有外部输入都不可信，包括文件、网络、串口、用户输入、配置、数据库记录。
2. 外部输入必须先校验长度、格式、范围、状态，再进入业务逻辑。
3. 文件路径必须防止路径穿越和非法拼接。
4. 敏感数据生命周期应尽量短，必要时主动清理。
5. 禁止引入未定义行为、空悬引用、越界访问和未初始化读取。

## 21. 性能规范

1. 先保证清晰和正确，再做优化。
2. 只有在有 profiler、压测或真实问题证据时才优化。
3. 读取路径优先用引用或视图，减少不必要拷贝。
4. 写入路径根据所有权选择移动语义。
5. 批量接口优先于逐条重复调用。

## 22. 构建与检查规范

1. 编译警告必须作为问题处理，不能长期堆积。
2. 推荐开启：`-Wall`、`-Wextra`、`-Wpedantic`、`-Wconversion`、`-Wshadow`。
3. 推荐结合 `clang-format`、`clang-tidy`、`cppcheck`、`asan`、`ubsan`、`tsan` 使用。
4. CI 至少应检查：编译、单元测试、静态检查、格式检查。
5. 新增测试、可执行文件和工具程序时，必须同步更新构建脚本，禁止出现“代码存在但构建系统不可见”的孤儿文件。
6. 提交前至少能说明本次修改对应的可执行验证命令，无法验证时必须明确写出原因和风险。

## 23. 提交前检查清单

1. 是否符合 C++17。
2. 是否遵守最小改动原则。
3. 是否仍满足头文件与源文件分离。
4. 类定义是否放在头文件。
5. 命名是否符合驼峰规范。
6. 类职责是否单一。
7. 函数是否过长或参数过多。
8. 错误处理风格是否统一。
9. 日志是否包含上下文。
10. 是否泄露敏感信息。
11. 是否存在裸 `new/delete`。
12. 是否滥用 `shared_ptr`。
13. 是否把业务逻辑写进 UI。
14. 是否直接依赖具体基础设施。
15. 是否存在隐藏全局状态。
16. 是否存在魔法数字。
17. 是否有未处理异常或线程退出风险。
18. 是否补充了必要测试。

## 24. 一句话要求

应用层 C++ 的目标是让业务边界更清楚、错误更容易定位、代码更容易维护；如果一段实现让系统更难理解，就说明它不符合本规范。
